输入输出（I/O）与副作用模型
================================================================================

在很多初学者的印象中，“纯函数式语言”似乎生活在一个与世隔绝的象牙塔中——函数必须满足严格的数学纯粹性，绝不允许产生任何副作用（Side Effect）。然而，一个无法读取键盘输入、无法在屏幕上打印日志、无法读写磁盘文件或调用网络接口的程序，在工业现实中毫无实用价值。

Haskell 是如何既坚守“纯函数引用透明”的数学原则，又能与充满不确定性的物理世界进行丰富交互的？本章将从底层哲学出发，彻底揭开 Haskell 的 **IO 单子**\ 之谜，并介绍工业级文件操作、资源管理与异常处理范式。

纯函数世界的困境：为什么需要特殊的 IO？
--------------------------------------------------------------------------------

要理解 Haskell 的 IO，首先必须理解它要解决的核心哲学矛盾：**引用透明性（Referential Transparency）**。

在纯函数式语言中，一个函数只要接收相同的输入，就\ **永远必须返回完全相同的结果**\ （如同数学中的 :math:`f(x) = x^2`）。此外，函数的调用绝不能对外部环境产生任何可观测的改变。

现在思考一个看似简单的控制台读取函数：

.. code:: text

   -- 假设存在这样一个纯函数：
   badGetLine :: String

如果 ``badGetLine`` 是一个纯函数，用户在终端第一次输入 ``"Alice"``\ ，第二次输入 ``"Bob"``\ ，那么在同一段代码中多次调用 ``badGetLine`` 就会产生不同的值！
这就意味着表达式 ``badGetLine == badGetLine`` 可能返回 ``False``\ ，数学上的“等式代换推导（Equational Reasoning）”将彻底崩溃，编译器的所有激进优化（如常量折叠、公共子表达式消除）都将引发不可预知的灾难。

因此，**Haskell 绝不允许有任何普通函数能直接从外部世界“抓取”数据或“污染”外部状态**。

IO 的核心心智模型：动作描述符与待办清单
--------------------------------------------------------------------------------

Haskell 解决这一难题的方案极其精妙且优雅：**将“执行副作用的过程”与“描述副作用的数据结构”彻底分离开来**。

1. IO 是动作描述符（Action Descriptor / Recipe）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Haskell 中，类型为 ``IO a`` 的值，**并不是已经执行完毕的结果，也不是正在执行的副作用过程，而是一份纯净、不可变的“动作描述符”（或者称之为一份“执行食谱”）**。

- 当你写下 ``putStrLn "Hello World"`` 时，它的类型是 ``IO ()``。
- 此时屏幕上**什么都不会打印**！代码所做的，仅仅是在内存中创建了一个小型数据结构，里面记录着：
  
  - 待执行的系统动作名称（如 ``writeToStdout``）；
  - 该动作所需的参数（如文本 ``"Hello World"``）。

创建这个动作描述符的过程是 **100% 纯粹且满足引用透明性** 的——你在代码里写 100 次 ``putStrLn "Hello"``，得到的是 100 个完全相同的动作描述数据。

2. 将动作交给外部运行环境执行
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

那么，这些动作究竟在什么时候才会真正变成物理屏幕上的像素或网络上的数据包呢？

整个 Haskell 程序的入口被强制定义为：

.. code:: haskell

   main :: IO ()

**程序员编写的全部 Haskell 代码，本质上是在用乐高积木搭建一个庞大的动作描述符——\ ``main``**。
当程序被编译并启动时，操作系统的 **GHC 运行时系统（Runtime System, RTS）** 会接管这个顶层动作，由外部运行时按照描述符中的指令依次执行系统调用。你的纯函数代码从未直接接触过硬件，它只是在“规划待办清单”。

3. IO 是保存动作结果的盒子（Monad 编排）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

如果一个动作在执行后会产生数据（例如从键盘读取一行文本），这个动作的类型就是 ``IO String``。

- 可以将 ``IO String`` 视为一个**保存了未来动作执行结果的密封盒子**。
- 为了防止不确定的外部数据污染纯逻辑世界，Haskell 严禁你直接把里面的纯值“掏”出来（标准库不存在合法的 ``IO a -> a`` 函数）。
- 现代软件绝大部分逻辑本质上是\ **一连串具备前后因果关系的 IO 动作**\ ——第 1 步读取配置文件，第 2 步根据配置内容连接数据库，第 3 步查询数据。

这正是 **Monad** 存在的最大意义：利用 ``>>=``\ （``flatMap``），我们可以将前一个动作盒子里产生的纯值，安全地传递给下一个动作描述符作为参数，动态编排出下一阶段的动作盒子！

.. tip::

   **如果你熟悉其他语言：IO 动作就像 Promise，do 记号就像 async/await**\ ：

   - **IO 动作与 JavaScript Promise**\ ：
     在 JS 中，调用异步函数返回的是一个 ``Promise<T>``\ ——它本身是一个携带了异步任务描述的对象，代表一个“未来的计算与结果”。Haskell 的 ``IO a`` 与之高度类似：传递的是动作描述，执行后在容器内交付结果。
   - **``do`` 记号与 ``async/await``**\ ：
     在 JavaScript 中，为了避免层层回调或不断手写 ``.then(res => ...)``\ ，现代标准引入了 ``async/await`` 语法糖。而在 Haskell 中，``do`` 记号正是 Monad 链式编排的 ``async/await``\ ：

     .. code:: haskell

        getUserInput :: IO ()
        getUserInput = do
          putStr "请输入姓名: "
          name <- getLine       -- 相当于 const name = await getLine();
          putStrLn ("你好, " ++ name)

     通过 ``name <- getLine``\ ，我们仿佛“解包”了盒子，把纯值 ``name`` 拿出来传递给下一行使用。而在编译器底层，这会被自动脱糖为标准的单子绑定管道（\ ``>>=``\ ）。

基础控制台 I/O
--------------------------------------------------------------------------------

Haskell 标准 Prelude 提供了最常用的终端交互函数：

.. code:: haskell

   putStrLn :: String -> IO ()        -- 输出字符串并追加换行符
   putStr   :: String -> IO ()        -- 输出字符串（不换行）
   getLine  :: IO String              -- 从标准输入读取一行文本
   print    :: Show a => a -> IO ()   -- 打印实现了 Show 的任何数据结构（等价于 putStrLn . show）

交互式完整示例：

.. code:: haskell

   main :: IO ()
   main = do
     putStr "请输入您的年龄: "
     ageStr <- getLine
     case reads ageStr of
       [(age, "")] ->
         putStrLn $ "明年您将 " ++ show (age + 1 :: Int) ++ " 岁。"
       _ ->
         putStrLn "输入格式有误，请输入纯数字！"

流式文件句柄与 RAII 资源安全
--------------------------------------------------------------------------------

基于 Handle 的流式操作
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在涉及文件、套接字等系统资源时，应当使用基于句柄（Handle）的操作规范。标准库 ``System.IO`` 提供了完善的生命周期管理：

.. code:: haskell

   import System.IO

   safeReadDemo :: FilePath -> IO ()
   safeReadDemo path =
     withFile path ReadMode $ \handle -> do
       contents <- hGetContents handle
       putStrLn "=== 文件内容 ==="
       putStr contents

``withFile`` 遵循现代编程语言的 RAII 规范（类似于 Python 的 ``with open(...) as f:`` 或 Java 的 try-with-resources）：无论作用域内的操作正常结束还是中途崩溃抛出异常，底层的文件句柄都保证会被操作系统即时、安全地关闭。

工程警示：致命的惰性 I/O 陷阱（Lazy I/O Pitfall）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Haskell 标准 Prelude 中提供了便捷的 ``readFile :: FilePath -> IO String``\ 。然而在生产级工程中，必须对它保持高度警惕！

.. warning::

   **惰性 I/O 的句柄死锁隐患**\ ：

   ``readFile`` 采用了早期的“惰性 I/O”机制——它不会立刻将整个文件读入内存，而是返回一个由惰性字符流构成的 String。底层的真实操作系统句柄会一直保持打开状态，直到这串字符在业务下游被彻底“按需消费完”才会关闭。

   - **文件句柄耗尽**\ ：如果你的函数只是读取了前几行就提前返回，句柄可能在很长一段时间内无法被垃圾回收，导致操作系统句柄耗尽崩溃。
   - **重入写锁冲突**\ ：如果在读取文件的同时，程序的其他模块试图修改该文件，会直接触发系统的文件锁定异常（ResourceBusy）。
   - **工程规范**\ ：在生产级项目中，**坚决避免使用 Prelude 的 ``readFile`` 与 ``hGetContents``**\ ；应当始终使用 ``Data.Text.IO`` 或 ``Data.ByteString`` 的严格读取函数（如 ``TIO.readFile``\ ），或者在超大文件场景下引入现代流式库（Streaming、Conduit 或 Pipes）。

终极资源管理范式：bracket
--------------------------------------------------------------------------------

在处理网络套接字、数据库连接池、分布式锁等复杂外部资源时，我们需要比 ``try-finally`` 更加强大可靠的保证。Haskell 提供了函数式资源管理的黄金法则——\ **bracket**\ 。

定义在 ``Control.Exception`` 中：

.. code:: haskell

   bracket :: IO a          -- 1. 资源分配动作（Allocate）
           -> (a -> IO b)   -- 2. 资源释放动作（Cleanup）
           -> (a -> IO c)   -- 3. 核心业务消费（Use）
           -> IO c

``bracket`` 的设计哲学极其严密：
1. 即使“业务消费”过程中发生不可恢复的致命异常、被异步信号打断、或是被外部线程取消（ThreadKilled），**清理动作也保证 100% 被执行**。
2. 在“资源分配”与“清理动作”注册之间，处于原子化屏蔽状态（Masked），杜绝资源泄漏的时间窗口。

实战案例：数据库连接的安全释放
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code:: haskell

   import Control.Exception (bracket)

   data DBConn = DBConn String

   openConn :: String -> IO DBConn
   openConn url = do
     putStrLn $ "==> 连接数据库: " ++ url
     return (DBConn url)

   closeConn :: DBConn -> IO ()
   closeConn (DBConn url) =
     putStrLn $ "<== 安全断开数据库连接: " ++ url

   runQuery :: DBConn -> IO ()
   runQuery (DBConn url) = do
     putStrLn $ "正在 " ++ url ++ " 上执行核心事务..."
     -- 即使在此处抛出运行时异常，closeConn 也必定执行！

   executeDatabaseTask :: IO ()
   executeDatabaseTask =
     bracket (openConn "postgres://localhost:5432/app")
             closeConn
             runQuery

运行时异常安全体系：Control.Exception
--------------------------------------------------------------------------------

在纯代码与 IO 之间，错误的分类非常清晰：

- **可预期的业务逻辑失败**\ ：必须使用纯函数式的 ``Maybe``\ 、\ ``Either`` 或 ``ExceptT``\ ，将错误显式声明在类型签名中；
- **外部环境的灾难性破坏**\ ：如磁盘扇区损坏、网络物理中断、权限不足，使用 ``Control.Exception`` 体系进行捕获与恢复。

使用 try 与 catch
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code:: haskell

   import Control.Exception
   import qualified Data.Text.IO as TIO
   import qualified Data.Text as T

   safeLoadConfig :: FilePath -> IO (Either IOException T.Text)
   safeLoadConfig path = try (TIO.readFile path)

   demoExceptionHandler :: IO ()
   demoExceptionHandler = do
     result <- safeLoadConfig "config.yaml"
     case result of
       Left ex ->
         putStrLn $ "加载配置失败，启动降级策略。底层原因: " ++ show ex
       Right content ->
         putStrLn $ "配置加载成功，大小: " ++ show (T.length content) ++ " 字符"

小结
--------------------------------------------------------------------------------

- **IO 不是副作用本身，而是描述副作用的纯净数据结构**\ （待办清单/食谱），最终在 ``main`` 中交由 GHC 运行时统筹执行。
- **IO 还是承载异步动作结果的密封盒子**\ ，类比于 JavaScript 的 ``Promise``；而 ``do`` 记号则是 Monad 的 ``async/await`` 语法糖。
- 绝不使用 Prelude 的惰性 ``readFile``\ ；流式资源必须使用 ``bracket`` 模式或基于 Handle 的严格读取。
- 业务错误使用 ``Either``\ ，系统级外部异常使用 ``Control.Exception`` 的 ``bracket`` 与 ``try`` 保障异常安全。
